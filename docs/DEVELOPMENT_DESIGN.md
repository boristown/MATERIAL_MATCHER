## 1. 项目背景与产品定位

本平台用于将客户侧物料主数据与集团物料主数据进行批量智能匹配，为每条客户物料推荐可信的集团物料候选，并在满足业务阈值时自动给出集团码；对于存在歧义、关键字段冲突或置信度不足的数据，进入人工确认；最终输出可追溯的集团码匹配结果和 Excel 文件。

13 所是首个真实落地客户，但产品从第一天起就按“**一套引擎、多客户配置**”设计，而不是为某一套表格、某一家单位或某一组物料类别编写一次性脚本。

产品目标可以概括为：

```text
不同客户、不同表头、不同物料类别、不同字段、不同权重
                    ↓
            通过配置描述差异
                    ↓
         共用同一套匹配引擎与平台
                    ↓
       自动匹配 + 人工确认 + 结果交付
```

### 1.1 业务价值

平台重点解决以下问题：

- 客户物料和集团物料字段结构不一致，无法简单按字段等值关联；
- 同一类物料可能存在名称、型号、规格、厂家、标准号等多字段差异；
- 大量物料需要在百万级集团物料中寻找候选，人工逐条处理成本不可接受；
- 不同物料类别的关键字段和匹配策略不同，不能使用单一固定算法；
- 低置信度匹配不能强行自动回填，必须保留人工判断能力；
- 匹配结果需要版本化、可解释、可复现、可追溯；
- 客户现场通常为内网、离线环境，部署和浏览器版本可能较旧。

### 1.2 产品不是“算法 Demo”

最终交付物不是一个相似度脚本，也不是一个只输出 TopN 的算法接口，而是一套完整 B/S 业务平台，包括：

- 匹配方案配置；
- 源数据上传与任务创建；
- 百万级目标库候选召回；
- 字段级精排评分；
- 实时计算看板；
- 人工确认工作台；
- 最终结果预览与 Excel 下载；
- 集团码目录和业务字典版本管理；
- 用户、角色、系统状态和运维能力；
- 银河麒麟 Linux V10 离线部署；
- Windows 7 客户端与浏览器版本门禁。

## 2. 核心设计原则

以下原则是项目红线。

### 2.1 客户差异配置化

底层不得出现类似：

```text
if customer == "13所"
if material_type == "A001"
if column_name == "某客户固定字段"
```

A001/A002/A003/A005/A006/A007、Z001/Z006 等只能存在于业务配置、客户专项文档或测试数据中，不属于平台固定枚举。

### 2.2 业务资产与技术资产分层

业务人员首先看到的是：

- 匹配方案；
- 匹配任务；
- 集团码目录；
- 业务字典；
- 人工确认；
- 最终结果。

文件 ID、索引 ID、算法名、物理文件路径、量化位宽、内部向量结构属于技术实现，不与业务资产放在同一视觉层级。只有管理员或运维排障时才进入高级信息。

### 2.3 低置信度宁可不匹配，也不错误回填

自动匹配必须满足阈值与冲突规则。人工待确认记录在用户真正确认前不得写入最终集团码。未处理 REVIEW 记录如果允许生成最终文件，其最终集团码必须保持为空。

### 2.4 配置与任务必须可复现

正式任务运行时冻结完整配置快照和哈希。后续修改方案、字典、目录激活版本都不能改变已经启动或已经完成任务的结果语义。

### 2.5 百万级数据不做全矩阵暴力比较

10 万 Source × 100 万 Target 不允许直接形成 1000 亿对完整评分矩阵。必须先通过分类、关键词、向量或其他召回方式缩小候选集，再执行高成本精排。

### 2.6 默认不擅自改变客户数据语义

默认处理流水线是 identity。大小写统一、标点清洗、单位换算、同义词、空值映射、数字容差等都必须由显式配置启用。系统不能“自作聪明”地偷偷改变物料原始含义。

### 2.7 前端必须真实连接后端

页面不得为了视觉演示而伪造业务状态、伪造下载、伪造统计值。UI 上出现的任务状态、进度、结果数量、目录版本、账号角色等必须来自真实 API。

## 3. 用户与角色

当前平台采用服务端 RBAC，正式角色为：

| 角色 | 定位 | 主要能力 |
|---|---|---|
| `admin` | 系统管理员 | 全部权限；账号、角色、系统设置、业务数据、任务、方案 |
| `operator` | 业务操作员 | 任务、方案、基础数据及正式业务操作 |
| `reviewer` | 复核人员 | 只读浏览 + 人工复核 + 最终结果/验收相关操作 |
| `viewer` | 只读用户 | 查看已授权信息，不执行修改 |

权限以服务端校验为准。前端隐藏按钮只用于改善体验，不能替代服务端授权。

系统禁止停用或降级最后一个有效管理员，避免出现无人可管理账号的状态。

会话由服务端维护，登出、账号停用、角色调整、密码重置等安全操作必须能够撤销相关会话。

## 4. 最新信息架构与导航

### 4.1 左侧主流程

最新 UI 不再把“匹配任务、匹配方案、人工复核、结果管理”做成互相割裂的普通菜单，而是把核心业务过程明确表达成四步：

```text
STEP 1 · 方案与配置
STEP 2 · 匹配计算
STEP 3 · 人工调整
STEP 4 · 输出结果
```

侧栏下方仅保留两个支撑入口：

```text
基础数据
系统设置
```

“支撑功能”这类无业务价值的标题不再显示。

### 4.2 品牌与页面壳层

左上角使用正式 SVG 品牌图形与“集团码匹配”中文名称，不显示多余英文副标题。顶部固定显示产品名称“物料集团码智能匹配平台”，右侧显示当前用户、角色和退出入口。

页面壳层原则：

- 左侧深色导航保持稳定；
- 主内容区使用浅灰背景与白色卡片；
- 关键操作使用统一蓝色主按钮；
- 绿色用于成功/已完成；
- 红色用于失败、危险操作和错误；
- 技术信息使用弱化样式，不抢业务操作视觉优先级。

### 4.3 页面路由

当前主要路由：

```text
/profiles                     STEP 1 方案与配置
/tasks                        STEP 2 匹配计算
/review                       STEP 3 人工调整
/results                      STEP 4 输出结果
/tasks/new                    创建任务 / 新建方案工作区
/tasks/:taskId                任务工作区/详情
/tasks/:taskId/evaluation     准确率验收
/data                         基础数据
/system                       系统设置
/login                        登录
```

STEP2、STEP3、STEP4 必须是独立页面文件，不能继续通过一个大页面依赖 `mode` 参数复用，否则多人并行开发时会互相覆盖，同时也会把不同业务职责重新耦合。

## 5. 总体业务流程

从业务角度，一次完整匹配过程是：

```text
准备匹配规则/选择已有方案
        ↓
创建匹配任务并上传客户数据
        ↓
冻结配置快照与基础数据版本
        ↓
STEP 2 匹配计算
        ↓
┌────────────────────┐
│存在待人工确认数据？│
└────────────────────┘
   ↓是              ↓否
STEP 3 人工调整      直接进入结果阶段
   ↓
STEP 4 输出结果
   ↓
预览 + 下载最终 Excel
```

后台仍可以把 STEP1 内部保存成“数据选择”和“规则确认”两个草稿子阶段，但这属于内部状态，不要求业务用户在侧栏看到五个步骤。

## 6. STEP 1：方案与配置

STEP1 解决的是两个不同业务动作：

1. **维护匹配方案**；
2. **使用已发布方案创建任务**。

过去这两个动作进入同一混合界面，导致用户不知道自己是在修改规则还是准备执行任务。v3.0 明确将二者拆开。

### 6.1 方案列表

方案首页以卡片展示可复用配置。卡片至少显示：

- 方案名称；
- 已发布版本；
- 是否存在草稿；
- 最近更新时间；
- 主要操作。

主要操作：

```text
[用此方案建任务] [编辑] [版本] [重命名] [删除(有权限时)]
```

要求：

- 4～5 个按钮在常见分辨率和长方案名称下不得超出卡片；
- 允许按钮自动换行，但排列必须整齐；
- 方案名称过长时优先换行或省略，不挤压操作区；
- 删除仅对有权限角色出现；
- 未发布方案不能直接用于正式任务。

### 6.2 “编辑”模式

点击“编辑”进入**方案配置模式**，目标是维护未来可复用的规则模板。

界面重点：

- 源字段与目标字段映射；
- 字段组合方式；
- 匹配方式；
- 权重；
- 关键字段；
- 匹配范围；
- 自动匹配阈值；
- 人工确认下限；
- TopN；
- 高级数据处理；
- 草稿保存；
- 发布；
- 版本历史与回滚。

**不显示**任务名称、正式源数据上传、启动匹配等执行任务操作，避免用户误以为编辑方案会直接运行数据。

### 6.3 “用此方案建任务”模式

点击“用此方案建任务”进入**创建任务模式**：

- 自动加载该方案最新已发布版本；
- 页面只显示必要的方案摘要，不展开完整规则编辑器；
- 用户输入任务名称；
- 上传本次待匹配客户物料；
- 确认使用的集团码目录/版本（如果方案已绑定，可默认带出）；
- 显示关键规则摘要；
- 启动正式任务。

如果业务需要允许“本次临时调整”，必须明确标注为“仅本任务生效”，修改结果写入任务配置快照，不能反向修改已发布方案。

### 6.4 新建方案

新建方案可以从样表或已有数据结构开始：

1. 上传/选择样例 Source 与 Target；
2. 自动识别字段；
3. 用户建立映射；
4. 设置算法、权重、阈值和范围；
5. 试算；
6. 保存草稿；
7. 发布正式版本。

### 6.5 方案版本语义

- 草稿可修改；
- 发布版本不可变；
- 回滚不是“覆盖旧版本”，而是基于历史版本生成一个新的正式版本；
- 任务引用已发布方案时记录 `profile_id + version`；
- 任务同时冻结完整 `config_snapshot + config_sha256`。

## 7. STEP 2：匹配计算

STEP2 是运行中心，不只是任务表格。

### 7.1 顶部运行态操作框

页面顶部优先展示当前/最近正在执行的任务。

运行中至少显示：

- 任务名称；
- 总体进度百分比；
- 当前业务阶段；
- 已处理/总行数；
- 已匹配集团码数量；
- 待人工确认数量；
- 未匹配数量（后端可提供时）；
- 当前吞吐；
- 已运行时间；
- 预计剩余时间；
- 预计完成时间；
- “进入实时看板”操作。

没有正在运行任务时，显示清晰空状态：

```text
无正在进行的任务
请通过 STEP 1 选择方案、上传数据并启动匹配任务。
[前往 STEP 1 配置并启动]
```

### 7.2 计算阶段

普通业务 UI 只展示可理解的阶段，例如：

```text
数据准备
目标数据准备/索引准备
候选召回
逐条精细评分
结果持久化
完成
```

不得在普通界面突出 BBQ、HNSW、SIMD、1-bit 等底层实现名词。

### 7.3 实时中间结果

计算过程中结果分批落库，页面可以预览最近处理记录。目的不是让用户提前修改结果，而是：

- 证明任务确实在运行；
- 及时发现输入数据或规则明显异常；
- 避免长时间运行时只有一个百分比进度条。

### 7.4 历史任务与草稿

顶部运行态操作框以下保留历史任务/草稿列表，视觉层级低于当前任务。

列表至少包含：

- 名称；
- 阶段；
- 进度；
- 状态；
- 更新时间；
- 操作。

状态包括运行、准备、排队、恢复、完成、失败、草稿等真实后端状态。失败任务不得显示为完成。

### 7.5 重启恢复

服务重启后任务状态必须能够从后端恢复。对于支持恢复的任务显示“恢复中”；无法从中间续算而选择安全重跑时，必须先清理本任务未完成的残留结果，防止重复数据。

## 8. STEP 3：人工调整

STEP3 是“人工处理工作台”，不能只有一个孤立任务列表。

### 8.1 顶部人工处理操作框

根据真实后端数据至少呈现三种状态。

#### 状态 A：存在可人工处理数据

显示：

- 当前/最近可处理任务；
- 任务名称；
- 待人工确认数量；
- 自动匹配/未匹配等摘要（后端可提供时）；
- 醒目的 `[进入人工调整]`。

#### 状态 B：STEP2 正在计算，暂时无可处理数据

显示：

```text
正在等待 STEP 2 计算完成
当前任务：xxx
当前进度：xx%
```

可显示实时进度，但不能出现“进入人工调整”主按钮，避免误导用户。

#### 状态 C：没有完成计算的数据

显示：

```text
当前没有计算完成的数据，请先启动 STEP 2 的数据计算。
```

提供前往 STEP2/STEP1 的正确入口。

### 8.2 人工工作台

进入具体任务后，默认只显示真正需要人工确认的数据，不把大量自动匹配结果混在首屏。

统计：

```text
待确认 | 已确认 | 自动匹配 | 未匹配
```

常用筛选：

- 高分但存在歧义；
- 第一/第二候选分差较小；
- 存在关键字段冲突；
- 指定分数区间；
- 全部待确认。

### 8.3 主表

推荐列：

```text
物料编码
物料名称/描述
第一候选集团码
第一候选分
第二候选分
分差
关键字段冲突
人工状态
操作
```

行操作：

```text
[查看候选] [确认候选] [标记未匹配]
```

允许批量确认第一候选和批量标记未匹配，但每次批量操作必须返回成功/失败明细。

### 8.4 候选详情

候选详情应在抽屉/工作台中打开，不让用户跳出当前上下文。

展示：

- TopN 候选；
- 集团码；
- 综合得分；
- 字段级客户值/集团值；
- 字段得分；
- 权重；
- 关键字段冲突；
- 选择当前候选或标记未匹配。

人工确认必须写入审计记录，保存操作者、时间和选择结果。

## 9. STEP 4：输出结果

STEP4 定位为“结果工作台”，不是普通历史任务表。

### 9.1 顶部最新结果操作框

默认展示**最近一次已经生成完成、可使用的正式结果**。

至少包含：

- 任务名称；
- 完成时间；
- 总行数；
- 自动匹配数量；
- 人工确认数量；
- 未匹配数量；
- 仍未处理数量（存在时）；
- 简洁结果预览；
- `[查看完整结果]`；
- `[下载 Excel]`。

下载必须调用真实结果/导出接口，不能在前端伪造文件。

### 9.2 无结果状态

必须区分两种情况。

#### 正在生成或等待前一步完成

显示当前任务、当前阶段和必要进度，引导用户等待或进入 STEP2/STEP3。

#### 从未生成结果

显示：

```text
尚无可下载结果
请先完成匹配计算，并在需要时完成人工调整。
```

### 9.3 历史结果

顶部最新结果以下保留历史结果任务列表，但视觉层级弱于当前结果操作框。历史结果可查看、下载和进入准确率验收。

### 9.4 正式 Excel

最终 Excel 至少包含：

1. 任务摘要；
2. 最终匹配结果；
3. TopN 候选；
4. 人工确认记录（如存在）。

编码类字段按文本写入，禁止集团码、物料号前导零丢失或被 Excel 自动转换为科学计数法。

## 10. 基础数据

基础数据页面只把**业务真正维护的资产**放在第一层级。

### 10.1 集团码目录

集团码目录是正式目标数据资产，支持：

- 上传集团码数据；
- 自动识别结构；
- 创建不可变版本；
- READY 状态；
- 激活一个当前版本；
- 上传新版本；
- 任务启动时冻结具体 `catalog_version_id`。

“当前”是一个激活指针，不代表旧版本被覆盖。历史任务永远引用当时的版本。

### 10.2 业务字典

业务字典用于显式的数据处理规则，例如同义词、规范值、别名或客户业务映射。

要求：

- 字典具有版本；
- 正式任务冻结字典 ID/版本或最终配置快照；
- 系统不得在未配置 `dictionary_map` 时偷偷做同义词替换；
- 修改字典不能改变历史任务结果。

### 10.3 文件资产

文件资产属于技术资产。普通业务页面不应把 `file_id`、物理文件、source/target/result 内部角色作为与集团码目录并列的核心业务概念。

如保留：

- 放入“高级信息/技术信息”；
- 默认折叠；
- 仅管理员/运维使用；
- 不删除后端文件 API 和运维追溯能力。

### 10.4 向量索引

向量索引同样属于技术资产。普通业务用户不需要理解 Index ID、`embedded_bbq_flat_v2`、量化算法等实现细节。

业务层只需要知道：

```text
集团码目录：已准备 / 正在准备 / 需要重新准备
```

管理员需要排障时才显示索引版本、行数、状态、创建时间和技术实现。

## 12. 数据输入与自动识别

### 12.1 支持格式

第一阶段支持：

- `.xlsx`；
- `.xlsm`（只读数据，不执行宏）；
- `.csv`。

所有物料号、集团码、分类码按字符串处理。

### 12.2 表格识别

系统不假定：

- 表头一定在第 1 行；
- Sheet 名固定；
- 物料号列名固定；
- 集团码列名固定。

上传后可识别：

- 工作表；
- 表头行；
- 字段列表；
- 样例数据；
- 可能的 ID 字段；
- 数据行数估计。

用户最终确认字段含义，系统推荐不能代替业务确认。

### 12.3 多表关联

允许多份客户数据通过配置化主键进行左关联或内关联。关联规则是配置的一部分，不写死 SAP 表名。

## 13. 字段映射与匹配规则

### 13.1 字段组合

支持：

- 一对一；
- 一对多；
- 多对一；
- 多对多。

组合方式包括：

```text
concat      拼接
coalesce    按优先级取首个有效值
best_of     多个组合中取最佳匹配
```

### 13.2 匹配方式

通用 matcher 包括：

```text
exact       精确匹配
contains    包含关系
fuzzy       字符串模糊相似
semantic    向量语义相似
hybrid      多方法综合
numeric     数值/尺寸类匹配
```

客户差异由 matcher 参数和处理流水线表达。

### 13.3 权重

业务界面、API 和配置统一使用 `0～100` 整数权重。

默认采用有效字段动态归一：

```text
raw_score = Σ(field_score × weight) / Σ(本条记录实际参与计算的有效 weight)
```

页面允许总权重不是 100，系统自动归一，不要求业务人员手工凑到 100。

### 13.4 关键字段

字段可标记为关键字段。关键字段发生明确冲突时，可以触发：

- 得分封顶；
- 转人工确认；
- 直接拒绝自动匹配。

具体策略配置化。

### 13.5 数值容差

数值匹配必须显式配置容差，不能默认把“接近”当作相同。支持：

- exact；
- absolute tolerance；
- relative tolerance；
- range。

---

## 14. 数据处理流水线与业务字典

每个字段的 Source/Target 两侧都可以配置处理步骤。

可选能力包括：

- trim；
- 大小写处理；
- 标点处理；
- 空值映射；
- 正则提取；
- 同义词/字典映射；
- 单位/尺寸处理；
- 标准号处理；
- 客户扩展插件。

**默认没有任何自动清洗步骤。** 新建规则时，若用户未配置，原值按 identity 进入 matcher。

这样做是为了防止平台在客户不知情的情况下改变语义，例如把大小写敏感型号、带斜杠的标准号或具有业务意义的空格错误归一化。

## 15. 匹配范围与分类策略

平台提供三种通用范围能力：

```text
GLOBAL   全库范围
STRICT   严格同类/同组范围
MAPPED   通过映射关系限定范围
```

分类/物料组本身是业务数据，不是引擎固定枚举。

例如首个客户可以将 A001 配置到元器件集团码目录，A003 配置到金属材料目录，A007 配置为跨类或其他范围；其他客户可以使用完全不同的编码体系而不改代码。

## 16. 候选召回与百万级目标库

### 16.1 两阶段设计

匹配过程分为：

```text
候选召回 Retrieval
        ↓
字段级精排 Rerank
```

召回目标是尽可能把正确候选带进 TopK，不直接决定最终集团码。

### 16.2 默认 Embedding

正式默认模型：

```text
BAAI/bge-base-zh-v1.5
```

默认 768 维，通过 Provider 配置替换。模型名、维度、最大长度、文本构造方式和处理流水线都属于索引版本的一部分。

### 16.3 向量存储

目标侧采用紧凑向量表示，当前设计以 1-bit BBQ 主体配合必要 sidecar/精排信息降低百万级索引内存和磁盘压力。Query 可以采用较高精度的量化表示用于召回。

这些技术细节只属于后端和管理员诊断，不出现在普通业务界面。

### 16.4 索引复用

只要以下内容不变：

- 集团码目录版本；
- Embedding 模型；
- Embedding 文本构造；
- 相关处理流水线；

现有索引必须复用，不得每次任务重新向量化 100 万 Target。

## 17. 综合评分与结果判定

### 17.1 三类结果

正式判定：

```text
AUTO_MATCHED    自动匹配
REVIEW          人工确认
UNMATCHED       未匹配
```

阈值满足：

```text
0 <= review_threshold < success_threshold <= 100
```

### 17.2 严格阈值

自动成功采用严格比较语义。显示分数只用于界面展示，不得改变真实业务判定。

### 17.3 同分歧义

如果第一候选和第二候选显示得分相同，但对应不同集团码，不能因为 Top1 排在前面就自动成功，应转入 REVIEW，避免随机排序决定集团码。

### 17.4 最终集团码

- AUTO_MATCHED：可以自动写入；
- REVIEW：人工确认前为空；
- UNMATCHED：为空；
- 人工确认后：写入人工选择的候选；
- 人工明确拒绝：保持为空。

正式任务至少冻结：

- Source 文件；
- 集团码目录版本；
- 方案来源（如有）；
- 完整配置快照；

- 字典/处理语义；
- 运行阶段；
- 状态；
- 进度；
- 结果文件引用。

### 18.3 业务阶段

```text
CALCULATE → REVIEW → RESULT
```

映射到前端：

```text
STEP2 → STEP3 → STEP4
```

如果无需人工确认，可以由 CALCULATE 直接进入 RESULT。

## 19. 实时进度与任务执行

任务进度接口应提供：

- 总体 progress；
- processed_rows / total_rows；
- current_phase；
- 阶段列表；
- live_counts；
- ETA；
- rows_per_minute；
- 最近中间结果。

ETA 是动态估算，不作为硬性完成承诺。首批样本不足时显示“估算中”，不要显示误导性的精确时间。

## 27. 可用性与视觉设计原则

### 27.1 业务优先

每个页面首屏优先回答：

```text
我现在处于哪一步？
现在有没有可以操作的数据？
系统正在做什么？
我下一步应该点击什么？
```

而不是先展示内部 ID、数据库状态或算法名。

### 27.2 关键操作框

STEP2、STEP3、STEP4 都采用“顶部业务操作框 + 下方历史列表”的结构：

- STEP2：当前运行任务；
- STEP3：当前可人工处理任务/等待状态；
- STEP4：最新正式结果预览/下载。

这使四步流程在视觉语义上保持一致。

### 27.3 状态设计

每个业务页面必须显式设计：

- 正常有数据；
- 空数据；
- 加载中；
- 后端失败；
- 无权限；
- 上一步尚未完成；
- 数据正在生成。

不能用空白区域代替状态说明。

### 27.4 响应式与对齐

至少验证常见桌面尺寸：

```text
1366 × 768
1920 × 1080
```

按钮、Tag、输入框、表格、标题操作区必须对齐；不能仅在开发者自己的分辨率下正确。

## 28. 错误处理与用户提示

错误信息分三层：

1. **业务提示**：用户下一步可以做什么；
2. **错误原因**：例如文件格式错误、字段缺失、权限不足；
3. **技术详情**：request_id、内部异常，仅在高级诊断中展示。

普通业务页面禁止直接把 Python traceback、SQLite 错误、绝对文件路径等原样暴露给用户。

## 29. 安全设计

- 密码不写日志；
- 会话服务端管理；
- 文件下载必须校验登记记录与权限；
- 前端不能传任意绝对路径要求后端删除；
- 账号启停/改角色/重置密码应影响现有会话；
- 管理员相关接口必须服务端校验 admin；
- 导出和人工确认必须记录操作者。

## 30. 准确率验收

平台区分三种不同指标：

### 30.1 候选召回 Recall

验证正确候选是否进入 TopK，只评价召回层。

### 30.2 自动匹配准确率

评价 AUTO_MATCHED 中真正正确的比例，这是业务风险最敏感指标。

### 30.3 端到端最终正确率

包含自动匹配和人工确认后的最终结果，与人工金标比较。

Synthetic 向量 benchmark 不能替代真实业务准确率。

例如：

- A001 可以绑定元器件目录和一套字段映射；
- A003 可以绑定金属材料目录和另一套规则；
- A007 可以选择跨类目录或其他策略；
- 下一家客户完全可以没有任何 A00x 类别。

不能把首个客户配置演变成核心代码分支。

---

## 33. 前端工程边界与多人并行开发

为了支持多个 Agent/开发人员同时修改不同页面，页面职责必须保持隔离：

```text
ProfilesView / TaskWorkspace     STEP1
TasksView                        STEP2
ReviewView                       STEP3
ResultsView                      STEP4
DataView                         基础数据
SystemView                       系统设置
```

页面专属样式优先放入：

```text
web/src/styles/pages/<page>.css
```

以下属于 shared infrastructure：

```text
App.vue
router.ts
api.ts
main.ts
styles.css
vite.config.ts
package.json
```

多个并行页面任务不应同时随意修改 shared infrastructure。需要公共能力时由单独 PR 或集成 Agent 统一处理。

详细规则见 [`FRONTEND_PARALLEL_DEVELOPMENT.md`](./FRONTEND_PARALLEL_DEVELOPMENT.md)。

---

## 34. 后端模块边界

建议保持：

```text
API 层
  ↓
Service / Domain
  ↓
Ingestion / Normalize / Matching / Retrieval / Vector
  ↓
Storage / Worker / Security
```

要求：

- API 层不实现匹配算法；
- 匹配核心不读取前端组件状态；
- 存储层不决定业务阈值；
- 权限只由服务端安全层判定；
- 客户插件通过稳定接口接入，不直接修改核心引擎。

截至 v1.0.10，四步页面隔离和旧浏览器门禁已经进入主线。本轮后续开发的目标设计为：

- 所有页面：禁止仅做 UI 不接真实 API。

这些不是临时美化项，而是本文 v3.0 的正式产品基线。

## 36. 项目完成定义

项目进入正式交付前必须同时满足：

1. 四步主流程可以由业务用户独立完成；
2. 方案编辑和任务执行语义清晰分离；
3. 百万级目标库不走全矩阵暴力计算；
4. Target 索引可复用；
5. 人工确认记录完整可追溯；
6. 最终结果可预览、可下载、可复现；
7. 业务基础数据与技术资产分层清晰；
8. admin/operator/reviewer/viewer 服务端权限通过；
9. 浏览器最低版本门禁生效；
10. 银河麒麟 V10 离线安装和 systemd 运行通过；
11. `/api/health`、`/api/health/ready` 通过；
12. 正式模型和真实数据完成准确率测试；
13. 至少完成一次正式规模端到端性能验收；
14. 最终执行生产就绪验收命令并保存证据。
