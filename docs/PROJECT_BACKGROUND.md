# MATERIAL_MATCHER 项目背景与设计约束

> 本文档用于记录当前已经确认的业务背景、产品定位和部署约束。后续详细架构、接口、算法与实施方案应在此基础上继续演进。

## 1. 项目定位

MATERIAL_MATCHER 的目标不是为某一家单位编写一次性的物料比对脚本，而是建设一个**通用的物料/实体匹配引擎**。

系统应能够面对不同客户、不同输入格式、不同字段结构和不同匹配规则，通过配置和可插拔组件完成数据匹配，而不是把客户特例硬编码进核心代码。

首个落地客户为 **13 所**。13 所用于验证首个真实业务场景，但**不作为核心架构的固定假设**。

核心设计原则：

- 核心代码不包含客户特例。
- 客户差异通过 profile / 配置表达。
- 输入输出格式采用适配器机制。
- 字段映射、标准化、召回、评分、决策策略彼此解耦。
- 匹配算法可替换、可组合、可评测。
- 匹配结果应可解释、可审计，并支持人工复核。

## 2. 首个业务场景：13 所集团物料匹配

当前已确认的首个落地场景如下：

- 客户侧约有 **10 万条物料**。
- 集团侧约有 **100 万条物料**。
- 集团物料数据来源于 SAP 表 `ZTMM_MARA`。
- 当前集团侧数据以 **Excel 文件**形式提供。
- 目标是在集团物料库中为客户侧物料寻找最可能对应的集团物料，并建立集团码映射关系。

该场景只是 MATERIAL_MATCHER 的第一套业务 profile。后续系统应能够支持其他单位、其他表结构、其他编码体系以及其他核对/匹配方式。

## 3. 当前匹配思路

当前讨论形成的初步方向为：

1. 对输入数据进行字段映射、清洗和标准化。
2. 从源数据和目标数据中选择参与匹配的关键字段。
3. 使用一种或多种候选召回方式缩小搜索空间。
4. 对候选记录进行多字段相似度计算。
5. 根据字段重要程度进行加权或其他形式的综合评分。
6. 输出 Top-K 候选结果，而不是只保留一个不可解释的最终值。
7. 根据阈值、唯一性、冲突等规则判断：
   - 自动确认；
   - 需要人工复核；
   - 无可靠匹配。
8. 记录总分、字段级得分、命中规则、置信度和最终决策依据，保证结果可追溯。

### 3.1 不绑定单一算法

系统不应被设计成“向量余弦相似度最高即匹配成功”。

候选召回和精排应支持多种策略，例如：

- 向量检索；
- 关键词/BM25；
- 精确字段过滤；
- 字符串模糊匹配；
- 编辑距离、Jaccard 等传统相似度；
- 规则评分；
- 多路召回融合；
- 模型重排或后续机器学习模型。

对物料主数据而言，型号、规格、牌号、技术标准、厂家等结构化信息往往具有很强的判别力，因此更倾向于采用“**高召回候选检索 + 结构化字段精排**”的混合模式。

## 4. 建议的核心抽象

系统长期目标可以抽象为：

```text
任意数据集 A
+ 任意数据集 B
+ 字段映射
+ 数据标准化规则
+ 候选召回策略
+ 匹配/评分策略
+ 决策策略
= 可解释的匹配结果
```

13 所场景只是其中一种配置：

```text
客户物料表
+ 集团物料表
+ 13 所字段映射与规则配置
= 集团码候选及最终映射结果
```

建议至少明确以下扩展点：

- `DataSourceAdapter`：Excel、CSV、数据库、API 等数据接入。
- `FieldMapper`：不同客户字段到内部语义字段的映射。
- `Normalizer`：单位、符号、大小写、空格、编码、同义词等标准化。
- `CandidateRetriever`：向量、关键词、规则、精确过滤等候选召回。
- `Matcher / Scorer`：字段级和综合相似度计算。
- `DecisionPolicy`：阈值、唯一性、拒识、人工复核等决策。
- `ResultExporter`：Excel、CSV、数据库、API 等输出。
- `Evaluator`：标准答案集和不同策略的统一评测。

## 5. 配置化原则

客户适配应尽量表现为独立 profile，而不是修改核心代码，例如：

```text
profiles/
├── customer-a.yaml
├── customer-b.yaml
└── 13th-institute.yaml
```

profile 可描述：

- 输入数据源；
- sheet / 表 / 接口信息；
- 字段映射；
- 参与匹配的字段；
- 字段权重；
- 标准化规则；
- 召回算法；
- Top-K 数量；
- 匹配阈值；
- 冲突和拒识规则；
- 输出字段。

字段名称、Excel 列名、SAP 表名等都不应成为核心代码中的固定常量。

## 6. 评测原则

系统需要独立的评测能力，以避免算法调整只能依赖主观判断。

建议逐步建立人工确认的标准答案集，并至少关注：

- Top-1 Accuracy；
- Top-K Recall；
- 自动确认覆盖率；
- 误匹配率；
- 拒识率；
- 人工复核率；
- 单条匹配耗时；
- 全量任务吞吐量。

所有重要算法和参数调整，应尽量通过同一套评测集进行前后对比。

## 7. 目标部署环境

当前首个目标服务端环境为：

- **银河麒麟 Linux V10**；
- 现场环境可能**没有 Docker**；
- 可能位于内网或离线网络；
- 不应依赖部署时访问公网下载第三方依赖；
- 尽量避免现场编译复杂 native 依赖。

因此，Docker / Kubernetes 只能作为**可选部署方式**，不能成为系统运行的前置条件。

### 7.1 推荐部署方式

第一阶段优先采用：

```text
离线安装包
+ 自包含运行时/依赖
+ 配置文件
+ install.sh
+ systemd 服务
```

目标是尽量做到：

```bash
tar -xzf material-matcher-<version>-<platform>.tar.gz
cd material-matcher-<version>-<platform>
sudo ./install.sh
```

安装过程中不访问公网，不要求用户手工执行大量 `pip install`，也不依赖系统已有 Python 环境的具体版本。

### 7.2 推荐目录约定

可优先考虑 Linux 常见目录布局：

```text
/opt/material-matcher/          # 应用和私有 runtime
/etc/material-matcher/          # 配置
/var/lib/material-matcher/      # 数据、索引、任务状态
/var/log/material-matcher/      # 日志
```

服务生命周期由 `systemd` 管理。

### 7.3 依赖打包原则

- Python runtime 和 Python 依赖尽量随安装介质交付。
- native library 尽量预构建并随平台包交付。
- 不依赖目标服务器现场联网下载。
- 不依赖目标服务器现场编译 gcc / C++ 扩展。
- 平台、CPU 架构和系统兼容矩阵需在真实服务器信息确认后固化。

## 8. 向量索引与模型的部署原则

由于目标现场可能没有 Docker，第一阶段不应把重型、独立部署的向量数据库作为硬性依赖。

建议抽象向量/候选索引接口，例如：

```text
VectorIndex
├── EmbeddedFaissIndex
├── EmbeddedHnswIndex
├── ExternalQdrantIndex
└── ExternalMilvusIndex
```

默认实现优先考虑嵌入式、本地可持久化方案，使 MATERIAL_MATCHER 可以作为单一服务独立运行；未来客户已有集团级向量平台时，再切换外部 backend。

Embedding 模型同样应通过 provider 抽象，不绑定某个固定模型或固定服务：

```text
EmbeddingProvider
├── LocalModel
├── LocalONNX
├── OpenAICompatibleAPI
└── ExternalHTTPService
```

程序包和模型包建议能够独立升级，避免模型文件较大时每次应用升级都重新分发全部模型。

## 9. 当前阶段

当前仓库处于**设计先行**阶段。

近期优先级为：

1. 完善开发设计文档；
2. 确认内部数据模型和插件边界；
3. 定义 profile 配置格式；
4. 定义首个 13 所数据字段映射；
5. 建立最小可评测基线；
6. 再进入核心代码实现。

在详细设计稳定前，不应为了第一个客户快速落地而提前把客户字段、Excel 格式或单一算法写死在代码中。

## 10. 待确认事项

后续需要进一步确认：

- 13 所客户侧源数据的实际 Excel 样例及字段定义；
- 集团 `ZTMM_MARA` 导出字段全集与数据质量；
- 集团码及可能存在的唯一性/一对多业务规则；
- 麒麟 V10 服务器的具体 SP、CPU 架构、glibc / Python 环境；
- 是否有 GPU，以及本地 embedding 的性能要求；
- 是否允许安装 RPM、systemd service 和自包含 runtime；
- 最终任务规模、执行频率和允许的处理窗口；
- 首批人工确认的标准答案数据，用于建立评测基线。
