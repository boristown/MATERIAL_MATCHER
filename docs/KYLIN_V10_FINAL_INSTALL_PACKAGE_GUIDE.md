# 银河麒麟 V10 最终安装包制作与非原厂安装验收手册

> **文档性质：最终安装包产品规格 + 非原厂安装说明 + 安装介质验收清单。**
>
> 本文不是“当前脚本已经全部实现”的声明，而是后续制作正式离线安装包时必须满足的目标合同。构建/运维 Agent 应从用户安装流程反向实现安装介质，并逐项通过本文验收。
>
> 目标平台：银河麒麟 Linux V10。默认优先交付 **Native Source（源码可见）离线安装包**；Docker Source 可作为受控环境下的可选交付，不作为普通用户默认安装路径。

**安装交互基线：命令行/终端优先（CLI-first）。** 最终安装包必须可在没有图形桌面的银河麒麟 V10 Server/最小化环境中完成首次安装、升级、维护和验收。`.desktop`、Zenity、KDialog、`pkexec` 等图形能力只能作为可选增强，不能成为安装成功或最终 PASS 的前提。

---

## 1. 最终目标

最终安装包必须做到：

**一名没有 MATERIAL_MATCHER 项目背景、不会 Python / Node / Docker / SQLite、但具有目标服务器管理员授权的普通运维人员，仅依照本手册即可在完全离线的银河麒麟 V10 服务器上完成首次安装、升级、基本验收和故障信息导出。**

普通安装人员不应该需要：

- clone Git 仓库；
- 访问公网；
- 手工执行 `pip` / `npm`；
- 自己创建 Python 虚拟环境；
- 自己安装 Python 依赖；
- 理解 wheelhouse、ONNX、tokenizer、SQLite 等内部概念；
- 手工编写 systemd service；
- 手工修改数据库；
- 手工寻找模型目录；
- 阅读源码才能判断是否安装成功。

允许普通安装人员具备：

- 能把安装介质拷贝到服务器；
- 能打开终端，进入安装介质目录并运行一个明确的 `启动安装.sh` 入口；
- 能进行系统管理员授权（root / sudo）；
- 能填写安装路径、端口和管理员初始密码；
- 能使用浏览器访问服务器地址。

**最终验收不是“脚本能跑”，而是“非原厂人员可独立完成”。**

---

## 2. 两类角色必须分开

本文同时服务两类角色，但职责必须严格区分。

### 2.1 安装人员（客户/非原厂）

只允许执行：

1. 检查安装介质目录完整；
2. 在终端进入安装介质目录并运行 `./启动安装.sh`；
3. 按终端交互向导填写少量业务信息；
4. 等待安装；
5. 打开浏览器并登录；
6. 按本文完成最小验收；
7. 若失败，导出诊断包并提交给原厂。

### 2.2 安装包制作人员（OpenCode / 运维 / 构建机）

负责：

- 冻结代码 commit 和版本；
- 准备目标架构 Runtime；
- 准备完整离线 wheelhouse；
- 准备正式 embedding 模型；
- 构建前端；
- 组装 release；
- 组装最终离线介质；
- 生成 manifest / SHA256；
- 制作 **terminal-first** 安装入口；图形入口仅作为可选增强；
- 在干净麒麟机做首次安装、升级、回滚、断网验证；
- 确认本文所有 MUST 项通过后才允许交付。

## 3. 非原厂人员看到的最终安装流程

最终交付必须把安装体验收敛成下面流程。

### 第 1 步：复制安装介质

把完整安装目录复制到服务器本地磁盘，例如：

```text
/home/admin/物料集团码智能匹配平台安装包/
```

不要直接从 U 盘运行正式安装，避免 U 盘拔出、只读挂载或 I/O 波动导致安装中断。

### 第 2 步：启动安装（默认命令行）

正式默认入口必须是终端模式：

```bash
cd "/home/admin/物料集团码智能匹配平台安装包"
./启动安装.sh
```

正常交付的介质必须保留脚本可执行位，不应要求用户额外执行 `chmod`。如果因为 U 盘/文件系统复制导致可执行位丢失，手册可以在“故障处理”中给出一次性 `chmod +x 启动安装.sh`，但这不能成为正常流程的隐藏步骤。

`启动安装.sh` 必须自行调用安装包内的 bootstrap runtime、完成环境检查，并在需要 root 权限时通过 `sudo` 提示用户授权。普通安装人员不直接调用底层 `install.sh`，也不需要理解环境变量。

如果系统存在图形桌面，可以额外提供：

```text
安装物料集团码智能匹配平台.desktop
```

但它只能是可选快捷入口，行为必须与 `./启动安装.sh` 完全一致。**没有桌面、没有 Zenity/KDialog、没有 pkexec 时仍必须完整安装。**

### 第 3 步：自动环境检查

向导必须自动完成并显示结果：

- 银河麒麟 V10；
- CPU 架构与安装包一致；
- systemd 可用；
- 安装介质完整性；
- 可用磁盘空间；
- 安装目录可用；
- 数据目录安全；
- 端口可用；
- 当前是首次安装还是升级；
- 是否检测到旧版本；
- 是否存在危险的“双 metadata DB”。

用户只看到“通过 / 失败 + 人能理解的处理建议”，不能看到一堆 Python traceback 作为主界面。

### 第 4 步：确认安装参数

首次安装只允许要求用户确认以下项目：

- 程序安装位置；
- 数据位置（默认自动选择，高级选项）；
- 服务端口；
- admin 初始密码（可手工输入或安全自动生成）。

默认值必须足以完成绝大多数安装。

建议默认：

```text
程序：/opt/material_matcher
配置：/etc/material_matcher
数据：由安装器安全选择并通过 /var/lib/material_matcher 统一访问
日志：/var/log/material_matcher
端口：18080（被占用时自动建议其它可用端口）
```

### 第 5 步：确认并开始

确认页必须显示：

- 产品名称；
- 安装包版本；
- CPU 架构；
- 首次安装 / 升级；
- 程序目录；
- 数据目录；
- 端口；
- 是否使用用户输入密码或自动生成密码；
- 升级时明确“保留账号、任务、数据库、索引和结果”。

### 第 6 步：安装过程

终端向导必须持续输出可理解的阶段和进度，例如：

1. 校验安装包；
2. 准备目录；
3. 准备运行环境；
4. 安装应用版本；
5. 安装模型；
6. 配置服务；
7. 启动服务；
8. 健康检查；
9. 完成。

详细技术日志写入安装日志文件；终端默认只显示阶段、进度、成功/失败和人类可读原因。任何预计超过 30 秒的阶段都必须持续给出进度或心跳信息，不能让用户判断不出是否卡死。

### 第 7 步：安装成功

安装成功后的终端输出必须至少显示：

- “安装成功”；
- 当前版本；
- 服务器访问地址；
- admin 账号；
- admin 初始密码或密码保存位置；
- 明确的本机 URL 与局域网 URL；图形环境可额外提供“打开系统”按钮；
- 安装报告保存路径；
- 中文维护工具的运行命令。

不能只显示 `127.0.0.1`。如果服务器存在可用局域网 IPv4，应同时显示至少一个可访问的局域网地址，例如：

```text
http://192.168.10.25:18080
```

### 第 8 步：最小业务验收

安装人员必须完成：

1. 浏览器打开系统；
2. admin 登录成功；
3. “系统设置 / 关于”显示的版本与安装包一致；
4. `/api/health` 正常；
5. `/api/health/ready` 正常；
6. 能进入第一步 · 数据上传；
7. 使用随安装介质提供的最小 smoke 数据完成一次测试，或运行系统提供的 smoke 工具；
8. 能下载结果文件。

这 8 项完成后，才能判定“安装成功”。

## 4. 最终安装介质必须包含什么

最终 Native Source 安装包根目录建议固定为：

```text
物料集团码智能匹配平台-<version>-kylin-v10-<arch>/
├── 启动安装.sh                         # 正式默认入口，CLI-first
├── 安装物料集团码智能匹配平台.desktop    # 可选图形快捷入口
├── install_wizard.sh
├── install.sh
├── verify_offline_bundle.py
├── offline-manifest.json
├── SHA256SUMS
├── BUILD_INFO.txt
├── README-安装前必读.txt
├── docs/
│   ├── 安装手册.md
│   ├── 维护手册.md
│   └── 故障处理.md
├── bootstrap/
│   └── ...                         # 安装器自用的最小自包含运行环境
├── release/
│   ├── runtime/
│   ├── web-dist/ 或 web/dist/
│   ├── source/
│   │   ├── src/material_matcher/
│   │   ├── web/
│   │   ├── scripts/
│   │   ├── installer/
│   │   └── pyproject.toml
│   ├── tools/
│   └── release-manifest.json
├── models/
│   └── BAAI/bge-base-zh-v1.5/
└── wheelhouse/
```

实际目录名可按构建脚本调整，但以下原则不可改变：

- 正式命令行入口 `启动安装.sh` 位于根目录，一眼能找到；图形快捷入口可选；
- 安装器不需要访问公网；
- Runtime、模型、依赖、前端、源码和 manifest 都随包携带；
- 源码可见；
- 前端 production `dist` 默认不携带无必要的 `.map` 文件；源码已经通过 `source/web` 单独保留；
- x86_64 与 aarch64 必须分别制作独立介质，不允许一个目录混装两套 native wheel；
- 安装手册随介质交付，不依赖访问 GitHub。

## 5. 最关键要求：最终包不能依赖目标机现装 Python

现阶段底层脚本存在调用系统 `python3` 的实现。**最终“非原厂可安装”版本必须消除对目标机额外 Python 环境的依赖。**

原因：

- 麒麟现场 Python 版本不可控；
- 系统 Python 可能过旧；
- 可能没有 pip；
- 可能缺少 urllib/json 之外的构建依赖；
- 非原厂人员不应临时安装 Python。

最终安装介质必须提供可用于以下动作的自包含 bootstrap runtime：

- 读取 manifest；
- 完整性校验；
- CPU 架构校验；
- 端口检测；
- readiness HTTP 检查；
- 必要的安装辅助脚本。

安装器启动优先级建议：

```text
安装包自带 bootstrap Python
    ↓
完成介质校验
    ↓
安装 release 自带正式 runtime
    ↓
正式服务只使用 release/runtime
```

系统自带 Python 只能作为兼容 fallback，不能作为最终交付前提。

## 6. 命令行安装向导必须满足的交互合同

### 6.1 CLI-first，GUI 仅可选

正式交付和最终验收必须以：

```bash
./启动安装.sh
```

为默认路径。安装向导必须在纯终端/SSH 会话中完整可用，采用清晰的一问一答式交互，不允许要求用户自己拼装环境变量或阅读源码。

存在图形桌面时，可以提供 `.desktop`、Zenity/KDialog 等快捷体验，但不得改变安装语义，也不得成为 PASS 的必要条件。

### 6.2 提权

命令行向导应支持：

1. 当前已经是 root：直接继续；
2. 普通管理员账号：通过 `sudo` 完成需要 root 的阶段。

若 `sudo` 不存在或账号无管理员权限，必须明确提示：

> 当前账号没有安装系统服务的权限，请切换到具备 root/sudo 权限的管理员账号后重新运行 `./启动安装.sh`。

`pkexec` 只属于可选 GUI 增强，不是标准安装前提。

### 6.3 密码

admin 密码：

- 可由用户输入；
- 可安全自动生成；
- 输入时不得明文回显；
- 自动生成后必须在终端成功信息中明确显示一次并提示立即保存，且不得写入世界可读日志；
- 密码文件只能 root 可读；
- 任何诊断包不得包含 admin 密码。

### 6.4 取消、中断与卡顿

在真正修改系统前可以安全退出。

进入写入阶段后：

- 首次安装：失败时清理未完成 staging，不删除用户已有目录；
- 升级：旧服务保持或恢复；
- 不允许留下半切换的 `current` 链接。

终端安装过程中任何长操作都必须给出阶段提示或心跳输出。**如果操作者需要因为“看起来卡住了”而另开终端排查，视为安装包缺陷，修复后必须从 clean snapshot 重新验证。**

### 6.5 可选图形入口

如果提供 `.desktop`：

- 只能调用与 CLI 相同的安装逻辑；
- 不能拥有另一套参数、数据路径或升级逻辑；
- 图形入口失败不得影响 CLI 安装；
- 本次最终 PASS 不要求存在桌面环境，也不要求验证 `pkexec`。

## 7. 首次安装的底层行为规范

首次安装必须自动：

1. 校验 bundle 完整性；
2. 校验目标 CPU；
3. 校验银河麒麟 V10；
4. 创建 `material_matcher` 系统用户；
5. 创建程序/配置/数据/日志目录；
6. 选择安全数据磁盘；
7. 写入唯一 `storage.env`；
8. 创建必要 SQLite 目录但不人为构造业务数据；
9. 安装 release；
10. 安装 embedding 模型；
11. 配置 systemd；
12. 设置目录权限；
13. 首次生成或保存 admin 初始密码；
14. 启动服务；
15. 执行 readiness；
16. 生成安装报告。

运行目录原则：

```text
/opt/material_matcher       程序和版本
/etc/material_matcher       配置
/var/lib/material_matcher   统一逻辑数据入口
/var/log/material_matcher   日志
```

## 7.1 安装完成后必须预置业务基础内容

正式客户安装完成后，系统不能是一个完全空白的“壳”。

本项目当前已经形成并在测试环境验证的 **6 个正式匹配方案**，必须作为安装包的默认业务种子数据随介质交付并在首次安装时导入。以构建时最新正式配置为准，当前方案集合包括：

- A001 元器件；
- A002 标准紧固件；
- A003 金属材料；
- A005 非金属材料；
- A006 复合材料；
- A007 物资类其他（跨类目）。

这些方案属于客户开箱即用所需的业务资产，不能只存在于外网测试环境数据库中。构建最终介质时必须从经过确认的正式配置来源导出为可追溯的 seed/template 文件，纳入 manifest 与版本管理。

同时，当前已经验证过的 **同义词/归一化配置** 也应作为默认种子版本随安装包交付。其产品语义继续保持：

```text
其他写法 → 标准写法
```

并在源数据与集团码目标数据两侧执行同一套归一化。

种子数据必须满足：

- 首次安装：如果系统中尚无对应业务配置，则导入默认 6 个方案和默认同义词版本；
- 升级：绝不能覆盖客户已经修改/发布的方案或同义词版本；
- 重装/修复：不得重复生成一批同名方案；
- 历史任务继续引用当时冻结的方案/同义词版本；
- seed 导入必须幂等；
- seed 文件、版本和来源 commit 必须可追溯；
- 不得把真实客户 Excel、账号、任务历史作为 seed 打包。

安装后的最小验收必须增加：

1. 登录后可以看到 6 个默认方案；
2. 方案名称、已发布版本及关键配置可打开；
3. “同义词配置”存在默认规则和明确版本；
4. 可使用默认方案直接创建 smoke 任务；
5. 升级已有系统后，客户自定义方案和同义词不被默认 seed 覆盖。

此外，同义词配置页面必须支持 **批量勾选 + 批量删除**，以便客户清理不需要的预置或后续规则。要求：

- 支持单条勾选；
- 支持本页全选/取消全选；
- 支持“删除已选 N 条”；
- 删除前二次确认；
- 保存后仍通过现有不可变版本机制形成新版本，不能直接修改历史版本；
- 不允许通过批量删除绕过并发/版本冲突保护；
- 对 100～300 条规则仍可正常操作。

这项 UI 能力如当前 main 尚未实现，应单独作为功能修复 PR 完成，并在重新构建最终安装介质前合入 main。

## 8. 数据目录是最高等级保护对象

`/etc/material_matcher/storage.env` 必须是持久化数据目录唯一来源。

升级、重装和修复均不得：

- 自动换到另一个磁盘；
- 因为 `/var/lib/material_matcher` 存在/不存在就重新猜数据目录；
- 创建第二份 metadata DB 后继续启动；
- 清空历史任务；
- 清空上传文件；
- 清空结果；
- 清空索引；
- 重置账号；
- 重置 session；
- 把“空库启动成功”误认为升级成功。

如果检测到：

```text
storage.env 指向 A
但 B 位置存在另一份 material_matcher.db
```

必须停止升级，提示：

> 检测到多个历史数据库，为避免账号和业务数据丢失，安装程序已停止。请导出诊断包并联系维护人员确认唯一数据目录。

不得自动选一个继续。

---

## 9. 升级必须先备份、后切换

正式安装包再次运行时，如果检测到已有版本，默认进入“升级”模式。

升级前必须自动记录：

- 当前版本；
- 当前 release 路径；
- 当前 model 路径；
- 当前数据目录；
- metadata DB 路径；
- 服务当前是否运行；
- 当前端口。

升级前必须生成至少：

- metadata DB 一致性备份；
- `/etc/material_matcher` 配置备份；
- 当前 release/model 指针快照。

升级固定顺序：

```text
校验新介质
→ 备份当前 DB/配置
→ 复制新 release/model 到 staging
→ 旧服务仍在线时对新版本执行 doctor
→ doctor 通过
→ 短暂停止旧服务
→ current/previous 原子切换
→ 启动新服务
→ readiness
→ 登录/版本 smoke
→ 成功
```

任何步骤失败：

```text
停止失败的新服务
→ current 恢复旧 release
→ model current 恢复旧 model
→ 恢复必要配置
→ 启动旧服务
→ 验证旧版本 health
→ 报告升级失败但旧系统已恢复
```

不允许失败后要求普通用户手工执行 symlink / systemctl 修复。

## 11. 最终包构建流程（制作人员执行）

### 11.1 冻结源代码

开始制作前：

1. 确认最终 `main` commit；
2. 所有计划进入安装包的功能 PR 已合并；
3. CI 全绿；
4. bump 最终版本；
5. 记录 commit SHA；
6. 构建期间不再混入新的功能修改。

### 11.2 准备 Python Runtime

目标：自包含、与目标 CPU 一致、可整体复制。

必须验证：

- `python3` 可执行；
- `pip check` 通过；
- FastAPI / NumPy / ONNX Runtime / tokenizers 等正式依赖可 import；
- 所有 native wheel 与目标 CPU 一致；
- Runtime 内 symlink 不逃逸到目标机系统路径；
- 完全断网仍能启动。

### 11.3 准备 wheelhouse

wheelhouse 必须包含：

- `pyproject.toml` 正式依赖；
- 全部传递依赖；
- `onnxruntime`；
- `tokenizers`；
- 对应目标架构的 native wheel。

制作阶段允许联网准备依赖，但正式离线包组装和目标机安装禁止联网补包。

### 11.4 准备模型

默认正式模型：

```text
BAAI/bge-base-zh-v1.5/
```

至少确认：

- tokenizer 文件完整；
- ONNX 模型完整；
- model ID 与 manifest 一致；
- 模型可以在目标 runtime 上加载；
- 断网可用。

### 11.5 构建 Vue production dist

必须在构建机完成，不要求客户现场首次安装时 npm build。

构建后：

- `index.html` 存在；
- favicon 正常；
- 登录页移动端资源正常；
- 默认不发布无必要 `.map`；
- 前端版本不硬编码；
- `npm run build` / `vue-tsc` / browser guard 通过。

### 11.6 构建 release

优先复用仓库正式构建脚本。

release 必须包含：

- 正式 runtime；
- 正式 web dist；
- 完整应用源码；
- 维护工具；
- `release-manifest.json`。

### 11.7 组装 offline bundle

使用 `scripts/build_offline_bundle.py` 或其后续正式替代脚本。

组装结果必须：

- 不联网；
- 自动验证 manifest；
- 检查文件 SHA256；
- 检查 target_arch；
- 检查模型；
- 检查 runtime；
- 检查 release；
- 检查未登记文件。

### 11.8 加入最终用户安装入口

最终交付介质必须补齐：

- `.desktop`；
- `启动安装.sh`；
- GUI/terminal wizard；
- bootstrap runtime；
- 本手册；
- 维护/故障手册；
- smoke 数据；
- `BUILD_INFO.txt`；
- `SHA256SUMS`。

最终 package builder 必须负责这些内容，不能靠现场人员从 GitHub 再下载。

## 13. 端口和网络访问规范

首次安装：

- 优先使用明确默认端口，例如 `18080`；

## 14. 安装成功判定标准

以下必须全部通过：

### 系统层

- systemd 服务 active；
- 开机启动已启用；
- `/api/health` 返回成功；
- `/api/health/ready` 返回 ready；
- embedding/model ready；
- frontend ready；
- release manifest ready。

### 浏览器层

- 登录页加载；
- favicon 正常；
- PC 浏览器可用；
- 移动端登录页不横向溢出；
- admin 可以登录；
- 关于页版本/commit 与安装包一致。

### 业务 smoke

至少完成一次最小业务流程：

```text
第一步 · 数据上传
→ 第二步 · 进度监控
→ 第三步 · 人工调整
→ 第四步 · 输出结果
```

smoke 数据应随安装介质提供，不能依赖客户自己准备。

安装 smoke 只验证软件可用，不替代正式准确率/规模验收。

## 17. 普通安装人员的故障处理表

最终手册/向导至少要覆盖：

| 现象 | 用户看到的解释 | 用户该做什么 |
|---|---|---|
| 不是银河麒麟 V10 | 当前安装包不支持此系统 | 停止安装，联系维护人员确认对应介质 |
| CPU 架构不一致 | 安装包架构与服务器不匹配 | 换用 x86_64 / aarch64 对应介质 |
| 安装包损坏 | 完整性校验失败 | 重新复制介质，不要继续安装 |
| 磁盘不足 | 安装或数据磁盘空间不足 | 清理或选择更大磁盘后重试 |
| 端口占用 | 默认端口不可用 | 接受向导建议的新端口 |
| 权限不足 | 当前账号不能安装系统服务 | 使用管理员授权重新运行 |
| 检测到两份 DB | 存在数据目录冲突，继续可能造成数据“消失” | 停止并导出诊断包 |
| 新版本 doctor 失败 | 新版本未达到切换条件 | 旧系统保持运行；导出诊断包 |
| readiness 失败 | 新版本启动不完整 | 安装器自动回滚；确认旧系统恢复 |
| 浏览器打不开 | 服务或网络访问异常 | 先查看维护工具状态，再由网络管理员确认端口 |

禁止只显示：

```text
Exit 1
Traceback ...
```

作为给普通用户的最终错误信息。

## 18. 最终安装包必须做的 Clean-room 验证

在交付前必须找一台**没有开发环境、没有仓库 checkout、没有提前安装项目依赖**的银河麒麟 V10 测试机。

测试人员最好不是开发者本人。

至少执行以下场景：

### 场景 A：首次安装

条件：

- 完全离线；
- 无项目 Python 环境；
- 无 Node；
- 无 npm；
- 无 Git 仓库；
- 只有系统正常组件和管理员授权。

要求：按本文操作安装成功。

### 场景 B：端口冲突

预占默认端口，确认向导能提示并选择其它端口。

### 场景 C：介质损坏

人为修改一个受 manifest 管理文件，确认安装在写系统前失败。

### 场景 D：重复安装同版本

确认不会覆盖成不同内容，不会清空数据。

### 场景 E：升级

从上一个正式版本升级到当前版本：

- 用户不丢；
- session 策略符合产品设计；
- 历史任务不丢；
- SQLite 不换库；
- 上传文件不丢；
- 结果不丢；
- 索引不丢。

### 场景 F：新版本启动失败

制造可控失败，确认自动恢复旧版本。

### 场景 G：双 DB 风险

构造两个 metadata DB，确认安装器拒绝自动选择。

### 场景 H：非原厂人员安装

让没有参与开发的人只看本文安装。

**如果需要开发人员远程指导敲额外命令才能成功，则本场景失败。**

## 23. Docker Source 的定位

Docker Source 只在客户明确允许 Docker/Compose 且有对应离线镜像治理能力时交付。

它同样必须满足：

- 完全离线；
- image tar 提前准备；
- 源码宿主机可见；
- 数据/config/log 使用宿主机 bind mount；
- 不把 metadata DB 放入匿名 volume；
- `docker compose down` 不丢数据；
- 有一键导入/启动入口；
- 非原厂人员不需要现场 `docker build`。

若客户环境没有 Docker，不得把 Docker 作为 Native Source 安装失败后的临时补救方案。
