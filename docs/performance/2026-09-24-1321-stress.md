2. 新瓶颈=RERANK(695/min)+PERSIST(20万候选行 30min) → 立项 **#199**（1.3.22 弹药：persist 批量化、rerank 多进程/向量化、workers 自适应默认）。

## 附二：十万级宽表压测与 ZIP64 修复（2026-09-25）
针对"新导出格式是否验证、十万级是否快、样式是否优化"三问的实测：
- **发现并修复致命缺陷**：100,000 行 × (8+80+20+20=129 列) + Top5 50 万行候选时，xlsxwriter 默认拒绝 >4GB zip 成员，导出 FileSizeError 崩溃（老 openpyxl 在此规模只会更慢，不会崩在 zip 上——此坑系新引擎引入）。修复：Workbook 选项 use_zip64=True。已合入 main、重建全量介质与增量包（新 SHA 见 media README），线上+测试床热替换复验 SMOKE 21/21。
- **十万级实测**：导出 421s（7 分钟）/327MB，峰值 RSS 20.2GB（大头是"整表读入内存"阶段），openpyxl 流式打开即读 100002×129。结论：**十万级宽表"能用但非秒级"**；若客户真到十万级×Top5，1.3.22 需做流式分块导出（读一段写一段）把内存压到 <4GB。
- **样式逐项审计**（对该 327MB 文件 XML 级验证）：四组合并表头行（匹配结果区|映射依据成对|源数据区|完整候选数据）、40 对 源·X|候选·X 严格相邻、一致性四色调色板齐全（E2F0D9/FFF2CC/FCE4D6/E7E6E6）、冻结前两行、文本列 @ 格式、五表结构完整。
